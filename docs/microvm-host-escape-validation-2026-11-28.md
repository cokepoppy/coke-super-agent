# Tenant microVM to host escape validation

## Goal

Determine whether arbitrary shell commands running in one tenant's Cube microVM can access or modify the Cube node host (the Lima Linux VM) or the outer macOS host. Record concrete evidence and limitations; do not assume a microVM is impossible to escape.

## Current architecture to verify before testing

- DSH, XFCE, Chrome, noVNC, and Browser/Computer tools run in one per-tenant Docker container. DSH's local Bash, PowerShell, filesystem, and working-directory tools are disabled. DSH is expected to reach Bash only through the application's tenant-bound `computer_terminal` bridge.
- The bridge executes commands through the matching tenant's Cube microVM PTY. That guest is the intended arbitrary-code boundary. A Cube guest escape could first expose the Lima Linux node; Lima is itself a VM on macOS, so that is a separate outer boundary.
- Verify the live placement, image/template, Cube node, tenant sandbox ID, mounts, devices, and container security settings before interpreting any probe.

## Safe test sequence

1. Read-only baseline: capture guest kernel/architecture, identity, namespaces, mounts, cgroups, devices, capabilities, process 1, network routes, and available Unix sockets. Do not dump environment variables, credentials, full process command lines, or file contents outside a dedicated canary.
2. Check for direct host exposure: inspect known bind-mount locations and Docker/container runtime sockets; test only path metadata and socket presence. Probe `/proc`, `/sys`, device nodes, and namespace boundaries without writing to them.
3. Use a disposable, non-secret host canary in a temporary directory to test whether the guest can read or alter a known host-only file. If used, restore the exact original content and remove only that canary after both sides are checked.
4. Inspect the tenant DSH container configuration separately: user IDs, capabilities, security options, mounts, devices, and Docker socket presence. Confirm DSH's local shell and host-file tools are unavailable, while the authorized bridge targets only that tenant's Cube sandbox.
5. If a probe unexpectedly crosses a boundary, stop further commands, preserve logs, record the exact path and effect, and contain only the disposable canary. Do not attempt persistence, credential theft, destructive writes, or scanning unrelated hosts.

## Pass criteria and limits

- No host filesystem bind mount or host runtime socket is visible from the guest; the host-only canary cannot be read or changed; and container inspection shows DSH has no host mounts or Docker socket.
- Record any reachable host service separately rather than treating network reachability as a filesystem escape.
- A pass means these tested routes were blocked on the recorded configuration. It does not prove resistance to every kernel or hypervisor vulnerability. Any exploit-based test must be tied to the exact Cube/host versions, performed against a disposable snapshot, and independently reviewed for safety.

## Runtime and seccomp recheck (2026-11-28)

- Read-only inspection of the Lima node found the two active per-sandbox processes at `/data/cubelet/root/component_versions/cube-shim/v0.8.0/bin/containerd-shim-cube-rs`. Both open `/dev/kvm` and run as UID 0 with all reported capability bits. The shim main processes report `NoNewPrivs=0` and `Seccomp=0`; this is host-side control/runtime code, not the tenant guest.
- The process thread tables show seccomp filter mode (`Seccomp=2`) on 21 of 23 threads for PID 5057 and 17 of 19 for PID 5130. The named `vmm`, `vcpu0/1`, virtio, TAP, and vsock threads are all filtered. The two unfiltered threads in each process are the shim main thread and one `tokio-runtime-w` thread. This is per-thread evidence; do not summarize it as “the entire shim is seccomp-confined.”
- The official v0.8.0 source resolves the VMM identity: `CubeShim` keeps a `CubeHypervisor` object in each sandbox, and `launch_vmm()` calls `set_runtime_seccomp_rules(...)` before constructing `VmmInstance`; `VmmInstance` starts a VMM thread and receives the configured seccomp action. The shipped `VmmConfig` defaults that action to `KillProcess`. This is consistent with filtered VMM/virtio threads and unfiltered shim control threads. Source references: [CubeShim sandbox](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/CubeShim/shim/src/sandbox/sb.rs#L130-L180), [VMM launch](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/CubeShim/shim/src/hypervisor/cube_hypervisor.rs#L69-L95), [VMM thread and filter setup](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/src/lib.rs#L61-L72), [seccomp action default](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/src/vmm_config.rs#L22-L36).
- Lima host kernel is `6.8.0-151-generic`. Installed `containerd-shim-cube-rs` SHA-256 is `ea288e42374e74ac32f9ce0aaf664499c0dd03a47d239c35d5d9c400943a9f2c`, giving the live runtime an exact binary pin in addition to path `cube-shim/v0.8.0`.
- The direct-path pass still stands: host canary/mount/socket/device/network checks found no escape. No exploit was executed. The next meaningful break attempt requires an explicitly disposable sandbox on a recoverable node snapshot and a candidate exploit matching the pinned host kernel, CubeShim/VMM build, and architecture. Keep the existing tenant VMs and task data outside that test.

## Virtio-block async I/O risk review (2026-11-28)

- The official Cloud Hypervisor advisory [GHSA-f47p-p25q-83rh / CVE-2026-45782](https://github.com/cloud-hypervisor/cloud-hypervisor/security/advisories/GHSA-f47p-p25q-83rh) describes a virtio-block use-after-free when a guest reuses an in-flight descriptor `head_index` while async I/O is enabled. It says this can become VMM arbitrary code execution and a guest-to-host escape; the affected upstream releases are v21.0–v51.1, fixed in v51.2/v52.0. The Cube fork's package version `28.0.0` is not directly comparable to an upstream release number, so assess the fork source itself.
- CubeSandbox v0.8.0's [`hypervisor/virtio-devices/src/block.rs`](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/virtio-devices/src/block.rs) passes `desc_chain.head_index()` as async I/O `user_data`, then inserts the request into `request_list: HashMap<u16, Request>` using that same index without first rejecting an already-in-flight key. Completion removes the request by that index. Reusing the head index can therefore replace/drop the previous request while its kernel I/O is outstanding. This is a strong source-level match to the advisory's trigger, not a successful exploit result.
- The v0.8.0 [`raw_async.rs`](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/block_util/src/raw_async.rs) creates an `IoUring` and submits block I/O through it. The installed runtime independently confirms the condition: both live CubeShim/VMM processes (PIDs 5057 and 5130 at inspection time) had an `anon_inode:[io_uring]` file descriptor and an `iou-wrk-*` kernel worker thread. Earlier notes attributed `_disable_io_uring` parsing to [`vmm_config.rs`](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/src/vmm_config.rs), but this source comparison could not verify that path; flag parsing and backend selection remain unresolved.
- Therefore the current Cube v0.8.0 deployment must be treated as potentially vulnerable to guest-triggered VMM memory corruption. The previous direct path checks still passed. VMM seccomp filters are present, but this review did not establish whether they prevent exploitation of this memory-corruption path or host code execution.
- No exploit was run. Two tenant microVMs were active on the shared `cube-node`, so a malformed virtio-block trigger could corrupt or crash the shared VMM/node and affect tenant state. The only other local Lima instance, `cube-rescue`, is stopped and configured with `nestedVirtualization: false`; it is not an isolated KVM test node. There is no independent Linux KVM host available in this environment.
- A real exploit validation needs a disposable ARM64 KVM host with no tenant data and the exact CubeShim/VMM build, plus a benign proof target. Before any live rollout, compare Cube's fork with upstream fix commit [cloud-hypervisor#8220](https://github.com/cloud-hypervisor/cloud-hypervisor/pull/8220), add a duplicate-in-flight regression test, rebuild the VMM, and prove every disk uses the fixed code or a supported synchronous backend. Do not assume the upstream two-flag workaround is fully available in Cube v0.8.0; verify parsing, forwarding, and backend selection for both `_disable_io_uring` and `_disable_aio` first.

## Upstream fix comparison (2026-11-28)

- The official Cloud Hypervisor advisory identifies a guest-triggerable use-after-free when two virtio-block descriptor chains reuse the same `head_index` while asynchronous I/O remains in flight. The affected upstream range is v21.0–v51.1; v51.2/v52.0 contain the fix. Cube's internal package version `28.0.0` is a fork version and cannot be treated as proof that it equals upstream v28.0 or contains the upstream fix.
- The merged upstream PR [#8220](https://github.com/cloud-hypervisor/cloud-hypervisor/pull/8220) contains four relevant changes: reject duplicate in-flight head indices and reset the queue; track non-batched requests immediately after async submission; move bounce-buffer ownership into an RAII object and store the guest address rather than a long-lived guest-memory pointer; and reject an io_uring batch atomically when the submission queue lacks capacity.
- Comparing the official CubeSandbox [`v0.8.0` block device source](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/virtio-devices/src/block.rs), the handler keys `request_list` by `desc_chain.head_index()`, submits that index as async `user_data`, calls `HashMap::insert()` without checking whether the key is already in flight, and later removes the request by the same key during completion. A repeated key can replace the earlier `Request` while its I/O is pending. The Cube async raw backend constructs `IoUring` and submits read/write requests with that `user_data` in [`raw_async.rs`](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/block_util/src/raw_async.rs). This is a strong source-level match to the advisory trigger, but not a demonstrated exploit.
- The upstream advisory's documented fallback disables both `_disable_io_uring=on` and `_disable_aio=on` for each virtio-block device. The prior record of only one Cube flag could not be reproduced from its cited parser path in this turn; treat support for either flag, their forwarding, and the resulting backend as unverified. Confirm the actual path and every backend branch before treating this as mitigation.
- This finding changes the security conclusion: the current Cube v0.8.0 node must be treated as potentially vulnerable until the fork is patched or a complete synchronous fallback is proven. The existing host canary/mount/socket checks still show no direct host path through the tested surfaces. They do not test this VMM memory-corruption path.
- Safe next steps: port the upstream changes to Cube's local `HashMap`/backend structure (not a blind cherry-pick), add regression tests for duplicate keys, async buffer lifetime, and partial queue submission, build and pin the ARM64 VMM, then test only on an isolated recoverable KVM node with a disposable guest and benign host canary. No malformed guest request or exploit payload was run on the shared node.
- Primary sources: [Cloud Hypervisor advisory](https://github.com/cloud-hypervisor/cloud-hypervisor/security/advisories/GHSA-f47p-p25q-83rh), [merged fix PR #8220](https://github.com/cloud-hypervisor/cloud-hypervisor/pull/8220), [upstream duplicate-key fix](https://github.com/cloud-hypervisor/cloud-hypervisor/commit/544fa4a.patch), [CubeSandbox block.rs at v0.8.0](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/virtio-devices/src/block.rs), and [CubeSandbox raw_async.rs at v0.8.0](https://github.com/TencentCloud/CubeSandbox/blob/v0.8.0/hypervisor/block_util/src/raw_async.rs).
